# 简历与面试说明

个人实施日期：2026-10-10；底座快照日期不等于个人项目开始日期。学习型框架，项目简介明确基于 guide-rpc-framework。

## 四条可据证据描述的工作

1. 基于成熟 RPC 底座完成 Java 8 环境固定、Netty/Hessian/GZIP 协议调用与 Spring 透明代理验证，保留原框架许可证和历史，跑通 ZooKeeper 双客户端端到端调用。通信、SPI 和代理来自上游，不能描述为全部从零实现。
2. 沿用 ZooKeeper 注册发现，验证正常注册/退出及相同接口不同 group/version 的服务与执行器定位；明确旧持久节点在宕机时的残留边界。本轮没有证明多实例宕机自动摘除。
3. 参考上游可靠性思路，新增入口超时、异步请求、失败/取消/断连统一收尾和按连接清理；27 个完整测试与 3 次定向回归通过，覆盖 3,000 次完成竞态，所测范围内 pending/计时任务最终为零。
4. 参考 Dubbo 隔离思路新增服务级有界线程池与明确过载响应，并建立 JMH + 固定到达率评测。在同机、快 100/慢 120 req/s、每组 3 次、过载窗口 15s 的初步实验中，快服务成功 P95 中位数从 1387.23ms 降至 1.94ms，成功率从 73.33% 到 100%。必须同时说明慢服务吞吐下降与短采样限制；不宣称整体优于 Dubbo。

正式对外简历若需要更稳定数字，应先执行长采样、核查生成器有效性及重复结果，再更新。勿把共享失败率省掉，勿把百分点写成相对百分比，勿使用单次 JMH 的秒级样本推断生产容量。

## 面试要点

- 原框架已有 DefaultEventExecutorGroup；自己的亮点是服务资源隔离、有界队列、请求可靠性和真实评测，不是第一次把业务移出 I/O 线程。V1/V2 都采用同一分发方式，避免把 Channel 串行效应混入隔离收益。
- PendingFuture 在终结前先从 Map 脱离并取消附属资源，再运行用户回调；定时任务晚挂接也立即取消。成功、失败、取消竞争只能有一个生效者；没有每请求关闭监听器，断连由每 Channel 的 Handler 处理。
- 超时从调用入口计时，发送前检查剩余时间。客户端取消不停止服务端任务，不自动重试非幂等调用。发现必须可中断或有自己的等待上限。
- shared 的线程可能集中用于慢服务，isolated 保护快服务但慢服务只剩 8 线程；8/0.2≈40 req/s 是粗略选压估算，不是实测吞吐保证。
- 成功 QPS 用完成窗口，成功率用该阶段发出的 cohort 跟踪至终结；分位数来自成功原始样本，拒绝/超时独立报告。JMH 闭环会随慢响应降速，隔离主结论用固定到达率。
- 关闭先拒绝新提交、关监听、限时排空/中断业务、处理未执行队列、再关 I/O；忽略中断的用户任务会被报告为关闭失败。
- 没有热调参、虚拟线程、远端取消、端到端 deadline 或 CompletionStage 服务端返回能力。旧注册路径不改，宕机摘除另行实现。
